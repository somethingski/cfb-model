# DECISIONS

Append-only log of non-obvious choices. Format: `YYYY-MM-DD | decision | rationale`.

| Date | Decision | Rationale |
|---|---|---|
| 2026-07-24 | Python **3.12.13** for the project venv (plan requires 3.11+) | 3.14.6 is also installed on this machine, but the scientific stack (pyarrow, LightGBM) does not reliably ship 3.14 wheels yet; 3.12 installs from wheels with no source builds. |
| 2026-07-24 | LightGBM as the GBT library (over XGBoost) | Faster iteration on small tabular data and native categorical handling. XGBoost was equally defensible; choice logged so Phase 5 does not relitigate it. |
| 2026-07-24 | `pyproject.toml` with an editable install, not `requirements.txt` | Single file for metadata and deps; `pip install -e .` makes `src/cfb` importable without path hacks. |
| 2026-07-24 | `src/` layout (`src/cfb/`) rather than a top-level `cfb/` package | Prevents accidentally importing the source tree instead of the installed package, which is how "works on my machine" test passes happen. |
| 2026-07-24 | Dependencies pinned with lower bounds (`>=`), not exact pins, at Phase 0 | Phase 0 has no numerical results to protect yet. Exact pins are added in Phase 7 alongside `make reproduce`, when reproducibility becomes a stated deliverable. |
| 2026-07-24 | Season range `2014–2025` lives only in `config.py` | Advancing to 2026 is a one-line change by design; no other module hardcodes it. |
| 2026-07-24 | Makefile targets stubbed with a failing `exit 1`, not a bare `echo` | `make reproduce` must fail loudly before the pipeline exists, so a green run can never be mistaken for a real one. |
| 2026-07-24 | `/games` is fetched **unfiltered** per season and narrowed client-side by `transform.is_fbs_involved` | The plan's `division=fbs` param is silently ignored by the current API — it returns D-II and D-III games (3,734 rows for 2023 vs 910 FBS-involved). The working filter is `classification=fbs`, but it keeps only games *hosted* by an FBS team and so drops the rare FBS-at-FCS game (Army at Yale, 2014 wk 5). Filtering client-side keeps the spine complete and makes the rule a tested pure function instead of a query param. |
| 2026-07-24 | Box-score stats stored as `stat_value REAL` **plus** `stat_raw TEXT` | Five categories are composites, not numbers: `possessionTime` (`"29:44"`), `completionAttempts`, `thirdDownEff`, `fourthDownEff`, `totalPenaltiesYards` (`"5-35"`). Splitting them into components is a modelling decision; ingestion stores the string verbatim and leaves `stat_value` NULL rather than deriving a number nobody asked for. Phase 4 decides what a composite means. |
| 2026-07-24 | CFBD's `homePregameElo`, `homePostgameElo`, postgame win probability, and excitement index are **not stored at all** | They are post-kickoff values that `/games` returns for free. A column that never enters the database cannot leak into a feature by accident, and Phase 3 builds its own Elo regardless. |
| 2026-07-24 | Spread sign convention: `spread` is stated from the **home team's** perspective (negative = home favoured), stored verbatim with no re-signing at ingest | Verified against 2023 Massachusetts vs Merrimack: `formattedSpread` `"Massachusetts -16.5"` with `spread: -16.5`. Phase 2's de-vig depends on this sign being right (RISKS #8), so it is recorded from an observed game rather than re-derived by guess later. |
| 2026-07-24 | `lines` also stores `spread_open` and `over_under_open` alongside the closing values | The stated benchmark is the *closing* line. Keeping the opener costs one column each and lets Phase 2 assert it is using the right one instead of assuming. |
| 2026-07-24 | Cache filenames are readable param slugs (`cache/games_teams/seasonType=regular__week=1__year=2023.json`), not the plan's param hash | When a season's row counts look wrong, the first question is always "which request produced this?". A slug answers it without a lookup table. The API key is never a query param, so nothing sensitive can reach a filename. |
| 2026-07-24 | `/games/teams` iterated over the weeks returned by `/calendar`, not a fixed `range(1, 16)` | The endpoint rejects a year-only call (week, team, or conference is required), and the calendar carries the postseason week, which a hardcoded range would silently miss. |
| 2026-07-24 | `games.start_date` is `NOT NULL` in the schema, not merely asserted after the fact | It is the canonical leakage clock. A game with no kickoff must fail at insert time rather than survive as a null that every later phase silently orders around. |
| 2026-07-24 | `team_seasons.classification` is recorded per season, recovered from the game payload for non-FBS opponents | `/teams/fbs` lists FBS teams only, but the game spine references FCS opponents as foreign keys, and teams move between subdivisions (James Madison, Liberty, Jacksonville State). Phase 3's FCS policy needs to know which season a team *was* FCS in. Copied from the API's own `homeClassification`/`awayClassification` fields, never inferred. |
| 2026-07-24 | A 200 response whose body contains a `message` key is treated as an error and is **not** cached | CFBD reports bad query params as HTTP 200 with a validation-message body. Caching one would poison the run with an empty result that looks like a legitimate answer on every subsequent run. |
| 2026-07-24 | The gold fixture is generated from the built database by `scripts/make_gold_fixture.py`, and `test_gold_games.py` **fails** until a human sets `human_verified: true` | Generating candidates from the same pipeline the test checks proves nothing on its own — a fresh fixture would pass its own test trivially. The failing gate is what converts it into evidence. A skip would be forgotten; a failure has to be dealt with. |
| 2026-07-24 | Gold fixture cases are pinned to specific seasons (2014, 2018–2023, 2025) rather than "first match" | Ordering by `game_id` is chronological, so every case otherwise landed in week 1 of 2014 — eight games that span one week are not a fixture that spans eras. |
| 2026-07-25 | Gold fixture pins Bovada for the 2023 away-favourite case, recorded in `PROVIDER_OVERRIDE` rather than left as a hand edit | Chosen during human verification because Bovada quotes both sides. Recording it in the generator means regenerating reproduces the committed fixture instead of silently reverting a verified decision back to DraftKings. |
| 2026-07-25 | **Phase 2.** Benchmark provider is chosen per game from a fixed 12-rung ladder (`consensus` → `Bovada` → `ESPN Bet` → `DraftKings` → `teamrankings` → …), and the winner is stored on the row | The plan assumed one provider could cover 2014–2025. Measured, none can: `consensus` runs 2014–2022 and stops during 2023 (29 games, then zero); Bovada runs 2019–2025. The seam therefore falls at the Phase 5 train/test boundary. A ladder keeps full coverage (10,277 of 10,374 games) and makes the switch visible in the data, where Phase 6 can report it, rather than hiding it in a season rule. Ordering is from measured coverage: `consensus` leads as a market aggregate rather than one book, Bovada follows as the only book spanning every test season. The four near-empty tail rungs are the sole source for two 2023 games. |
| 2026-07-25 | **Phase 2.** `p_home_devig` is **always spread-derived**, even for the 2021+ games that also carry moneylines; the moneyline probability is stored beside it in `p_home_moneyline` | Moneylines exist only from 2021 (RISKS #15), so "moneyline preferred, spread fallback" would change the benchmark's construction at 2021 — one season before the validation year and two before the test set. The model would then be measured against a differently-built object on the seasons that matter most. A uniform spread-derived yardstick costs one column and turns the moneyline view into a free Phase 6 sensitivity check instead of a confound. Measured agreement between the two on the 3,933 games that have both: mean absolute gap 0.0315. That decision then paid for itself immediately — see the neutral-site moneyline row below. |
| 2026-07-25 | **Phase 2.** The 31 rows where the moneyline and the spread disagree about who is favoured by more than 0.25 are **kept as-is, counted in the coverage report, and pinned by a test** — not dropped, not corrected | Found by the spread-vs-moneyline cross-check: 28 of the 31 are neutral-site games and 26 are postseason. The inversion rate is 8.8% of neutral-site rows (28 of 320) against 0.1% of ordinary home games (3 of 3,612), so CFBD's Bovada home/away assignment for a neutral-site game does not always match the perspective its spread is stated from. Individual cases adjudicate clearly against the moneyline (2021 Gator Bowl: Rutgers listed +16.5 on the spread but −750 on the moneyline, and lost 10–38), but with n=31 the outcomes do not settle it in aggregate, so re-signing them would be a guess applied to the yardstick. Only `p_home_moneyline` is affected; `p_home_devig` is spread-derived and untouched. Phase 6 must exclude these rows from the moneyline sensitivity check rather than average over them. Recorded in RISKS #16. |
| 2026-07-25 | **Phase 2.** σ = **15.9850** points, fitted on 2014–2021 only, as the root-mean-square of `(actual_margin + spread)` **about zero** rather than the sample standard deviation about its own mean | The conversion `p_home = Φ(-spread/σ)` assumes a zero-mean residual, so the σ that belongs in it is the RMS about zero. Fitting an intercept as well was considered and rejected: the mean residual is −0.372 points against a σ near 16, which moves any probability by under 0.01 and is more likely training-set noise than signal. `estimate_sigma` raises on any season past `config.TRAIN_LAST_SEASON`; that guard is this phase's leakage boundary and has a poisoned-input test. |
| 2026-07-25 | **Phase 2.** De-vig is multiplicative; `p_away` is computed as `1 - p_home`, not by its own division | Multiplicative normalisation is the transparent, interview-defensible baseline. Shin corrects for insider-trading asymmetry that matters more in thin markets than in heavily-traded CFB closing lines, and since the benchmark scores rather than bets, the refinement moves the yardstick by less than model noise — noted as a Phase 6 robustness check, not a requirement. The `1 - p_home` spelling is not cosmetic: two independent divisions sum to 0.9999999999999999 on some real quotes, and exit criterion 3 asks for an exact sum. |
| 2026-07-25 | **Phase 2.** One-sided moneylines (58 rows) are treated as absent, not paired with an inferred opposite price | De-vigging needs two prices to normalise against. Inventing the second one would be imputation in the one table the whole project is measured against. |
| 2026-07-25 | **Phase 2.** Benchmark probabilities are **not clipped**; the plan's exit criterion "no probabilities outside (0.01, 0.99)" was amended rather than met | 504 games (4.9%) fall outside that band under a spread-derived benchmark, which the criterion did not anticipate — it assumed moneylines, and books rarely quote past ~0.95. Clipping is the over-claim direction: among the 319 training games with `\|spread\| ≥ 37` the favourite won 318 (99.7%) against the normal model's ~99%, so the model is if anything underconfident at the tail and clipping to 0.99 would understate a real effect, weakening the benchmark and making it easier to "approach". Confirmed by Sean before the amendment was written. Tail count is printed on every build; RISKS #17. |
| 2026-07-25 | **Phase 2.** `gold/vegas_fixture.json` is emitted with `hand_computed` **null** and the test fails until a human fills it in | The Phase 1 fixture could be proposed complete because a human checks it against collegefootballdata.com — an external source. A de-vigged probability has no external source to check against, so if the generator proposed the answers it would be grading its own arithmetic. The human's independent numbers are the only thing that makes this fixture evidence. |
| 2026-07-25 | **Phase 3.** Every FCS opponent is rated a fixed **1200** that never updates, while its FBS opponent updates normally | Confirmed by Sean before any code was written, per the plan's decision point. Excluding the 1,288 FBS-vs-FCS games would discard real information — a team that loses to an FCS opponent has to look worse afterwards — while tracking FCS ratings properly would mean carrying ~117 teams whose schedules this database barely observes. A fixed reference point keeps the information and costs one constant. The asymmetry is deliberate and lives in `RatingBook.apply`: the delta is computed zero-sum by the engine and then applied to the FBS side only. |
| 2026-07-25 | **Phase 3.** Subdivision is read **per season** from `team_seasons`: a team entering FBS starts at 1300, a team leaving FBS has its rating discarded, and a team returning would restart at 1300 rather than resume | The plan covered teams entering FBS but not leaving. Nine teams move up in range (Charlotte 2015 through Delaware and Missouri State 2025) and **Idaho moves down** in 2018, so the rule was needed either way. Confirmed by Sean. Resuming a stored rating after a spell in FCS would apply a rating years out of date to a roster that no longer exists; the newcomer prior is a worse fit for nobody and a better fit for that case. No team returns within 2014-2025, so this branch is exercised only by `test_a_team_leaving_fbs_is_dropped_and_restarts_on_return`. |
| 2026-07-25 | **Phase 3.** The MOV multiplier uses the **signed** winner-perspective Elo difference, not the plan's `\|elo_diff\|` | The plan named the FiveThirtyEight form and then transcribed it with an absolute value. The two disagree: the signed denominator shrinks the multiplier when the favourite wins and grows it when the underdog does, which is precisely the anti-autocorrelation property the plan's own rationale asks for, while the absolute value damps upsets exactly as hard as expected blowouts and deletes it. Followed the named form. The guard for a negative denominator (`winner_elo_diff < -2200`) raises rather than silently flipping sign; it is unreachable at these ratings, where the widest gap the system produces is about 850. |
| 2026-07-25 | **Phase 3.** The tuning objective is log loss on **completed FBS-vs-FBS games in 2014-2021 only** | Confirmed by Sean. Games against a fixed-1200 opponent are near-foregone conclusions, so including them would let the grid buy log loss on games the project never models and would tune K partly against the FCS constant; `RISKS.md` #3 keeps those games out of Phase 5 training on the same reasoning. Log loss rather than Brier because it punishes confident misses harder, which is exactly the failure mode an over-large K produces. `grid_search` raises on any season past `config.TRAIN_LAST_SEASON` and the walk is loaded with `through_season` set, so the search never even reads a validation or test season. |
| 2026-07-25 | **Phase 3.** The pre-season regression grid was **widened below the plan's `{1/4, 1/3, 1/2}`** to `{0, 0.10, 0.15, 0.20, 0.25, 1/3, 1/2}` | On the plan's three candidates the winner was 1/4 — the lowest, i.e. a grid edge, which exit criterion 3 defines as evidence the grid is wrong rather than as a result. Widening as the criterion prescribes produced a clean interior minimum at **0.20** (log loss 0.55199 against 0.55212 at 0.25). `0.0` was kept in the grid deliberately as the null: it scores 0.55798, clearly worse, which is what earns pre-season regression its place instead of assuming it. The 0.20-vs-0.25 difference is 0.0001 in log loss and is noise; the 0.20-vs-0.5 difference is not. |
| 2026-07-25 | **Phase 3.** Frozen parameters: **K = 37.5, HFA = 50, regression = 0.20**, fitted on 2014-2021 over a 1,001-point grid and written to a committed `elo_params.json` | Every later phase reads the file rather than re-fitting, so the training-season boundary is enforced by there being only one place the values come from. All three are interior to their grids. HFA = 50 is lower than the ~65 the plan assumed and lower than the folklore figure, but the objective is flat between 45 and 55 (0.55199-0.55231), so the honest reading is "somewhere around 50", not "exactly 50". `mean`, `initial`, `newcomer` and `fcs` are priors chosen before any fitting and are deliberately kept out of the grid. |
| 2026-07-25 | **Phase 3.** Only **pre-game** ratings reach the database; there is no post-game column | Same reasoning that kept CFBD's `homePostgameElo` out of the Phase 1 schema: a post-game rating is one join away from becoming a feature that knows the result of its own game. Post-game values exist only inside the walk. |
| 2026-07-25 | **Phase 3.** The season boundary is detected by the `season` field changing during the **chronological** walk | Verified against the data rather than assumed: `season` never decreases in `(start_date, game_id)` order, because season S's bowls kick off before season S+1's opener. This also handles `RISKS.md` #13 correctly — the two 2020-stamped New Mexico State games played in Feb/Mar 2021 sit at the end of 2020, which is where they belong. Ordering by `(season, week)` would have put them in the wrong place. |
| 2026-07-25 | **Phase 3.** A tie produces **no rating change at all**, and this is documented rather than patched | `ln(\|0\| + 1) = 0`, so the MOV multiplier is zero and the `S = 0.5` branch moves nothing. College football has had overtime since 1996 and the database contains 0 ties in 10,373 completed games. The alternative — a floor of 1 on the margin — would be inventing an input to cover a case that does not occur. Pinned by `test_a_tie_moves_nothing` so the behaviour is a decision rather than an accident. |
| 2026-07-26 | **Phase 3.** `gold/elo_fixture.json` asks for **post-game** ratings, and the test chains them forward itself to check the pre-game column | The worksheet originally asked for pre-game ratings, which is the column the pipeline stores — but it is not what a hand computation produces. You cannot reach game 5's pre-game ratings without having worked out games 1-4, so the natural output of the exercise is "what each team carried out of each game", and Sean filled the pre-game slots with post-game values. His arithmetic matched the engine to 8 decimal places on all 12 values; only the labels were wrong. Relabelled rather than recomputed, and `test_stored_pregame_ratings_are_the_hand_computed_chain` now derives the stored column from his numbers, applying the regression with the formula written out in the test rather than by calling `run_season_regression`, so it remains a check on the code and not a restatement of it. Verified to still fail: perturbing one hand-computed value by 0.001 fails three tests. |
| 2026-07-25 | **Phase 3.** The naive home baseline predicts the **training-season** home-win rate (0.5754) for every game, including held-out seasons | Using each season's own home-win rate would be a season-level aggregate applied to games inside that season — the exact leakage pattern `CLAUDE.md` names, and it would flatter the baseline the model is supposed to beat. |
| 2026-07-24 | The backfill reports its network-vs-cache request counts on every run | Exit criterion 1 ("hits the API zero times on the second run") is otherwise an assumption. Printing `0 network, 257 from cache` makes it something you can read off the run instead of trust. |
